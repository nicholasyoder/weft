# Visual realism plan

**Working checklist, not a spec — same living-document rule as the rest of `docs/roadmap/`.** Addresses all four items in Tier 2's ["Visual & gameplay realism"](tier-2-visual-and-gameplay-realism.md) that are still open: PBR material model, normal mapping, multiple scene-authorable lights, and shadow mapping. Today `Material` (`crates/engine-render/src/components.rs`) is a flat base color plus one optional texture, explicitly documented as "Full PBR is not a goal"; `shader.wgsl`/`skinned_shader.wgsl` (`crates/engine-render/src/`) both hardcode identical Lambertian-plus-flat-ambient math against a single `const LIGHT_DIR: Vec3` baked directly into `gpu.rs` — not a component, not scene-authorable, and no scene can add a second light or a point/spot light at all. `Vertex`/`SkinnedVertex` (`crates/engine-render/src/mesh.rs`) carry `position`/`normal`/`uv` only, no tangent — normal mapping is structurally blocked, per the tier doc's own words. No shadow pass exists.

Split into 7 phases, same discipline [`physics-substrate-plan.md`](https://github.com/nicholasyoder/weft/blob/4fcb7a9/docs/roadmap/physics-substrate-plan.md)/`debt-cleanup-plan.md` used (both now retired, their work done): each phase lands as its own reviewable, tested commit, full gate clean before moving to the next — `cargo test --workspace`, `cargo clippy --workspace --all-targets -- -D warnings`, `cargo fmt --all -- --check`.

**Design decisions made up front** (don't re-litigate without a reason — see the ADR once Phase 7 writes it):

- **PBR shading: metallic-roughness workflow, Cook-Torrance GGX / Schlick-Fresnel / Smith-visibility, single hardcoded ambient term kept.** The standard real-time formulation (as in Karis 2013, "Real Shading in Unreal Engine 4") — GGX normal distribution, Schlick's approximation for Fresnel (F0 = mix(0.04, albedo, metallic)), Smith geometry/visibility term, Lambertian diffuse scaled by `(1 - metallic)`. The existing flat `ambient = 0.15` term is kept as-is for now (a placeholder for missing image-based lighting) — no environment/IBL lighting is a goal of this arc; revisit when that becomes a concrete need.
- **`Material` gains `roughness: f32` (default `1.0`) and `metallic: f32` (default `0.0`), not a combined "PBR" flag.** Defaults chosen so an *unmodified* existing scene file (fully rough, fully dielectric) renders as close as possible to its old Lambertian look, minimizing (not eliminating — the BRDF itself changes) visual drift for content nobody touches.
- **Texture bind group grows entries, not bind groups.** wgpu 30's real `Limits::default()`/`downlevel_defaults()` both report `max_bind_groups: 4` (verified against the pinned `wgpu-types-30.0.1` source) vs. `max_bindings_per_bind_group: 1000` — the skinned pipeline already sits at 3 groups today. `texture_bind_group_layout` (`gpu.rs`) grows from 2 entries to 4 over Phases 2-3 (base color tex/sampler, then metallic-roughness tex, then normal tex — one shared sampler for all), instead of a new bind group per texture type. Rejected alternative: a bind group per texture — would exceed the 4-group ceiling once shadow mapping's own resources land in Phase 5.
- **Lights: a small fixed-size array in a uniform buffer (`array<GpuLight, 4>`), not a `storage` buffer like `joint_matrices`.** Verified against naga 30.0.1's real layouter (`Alignment::MIN_UNIFORM = 16`): a `GpuLight` built from two `vec4<f32>`s is inherently 16-byte-strided, satisfying WGSL's uniform-array alignment rule with no manual padding. Unlike joints (genuinely per-skin unbounded), no concrete scene needs more than a handful of lights — a fixed cap of 4 fits comfortably inside the guaranteed 64 KiB uniform binding size and avoids a second `storage`-typed bind group. Rejected: unbounded storage-buffer lights — no consumer needs it, and it would just be copying the joints pattern reflexively rather than for a real reason.
- **One new shared "lighting" bind group carries lights, the shadow map, and the shadow comparison sampler together** — not three separate groups. Keeps the skinned pipeline's total bind-group count at exactly 4 (uniform, texture, joint, lighting), at wgpu's confirmed default limit but never over it.
- **Tangents: a new sibling asset type (`engine_assets::tangent::TangentData`), never a field added to `MeshData`.** `MeshData`'s encode/decode (`crates/engine-assets/src/mesh.rs`) go straight through `bincode`, which — confirmed via bincode 1.3.3's own readme — implements no versioning scheme at all; `#[serde(default)]` does nothing for a positional format like bincode, so adding a field there would corrupt/fail-to-decode every already-committed mesh blob in `games/sandbox/assets/` and `crates/engine-assets/tests/fixtures/`. This is exactly the constraint ADR-0015/Phase 13 already solved for skinning (`SkinData`/`Skeleton` as separate content-addressed blobs, joined at GPU-upload time in `mesh.rs::from_skinned_asset`) — the same shape is reused here. `MeshRef` gains `tangent: Option<String>` (`#[serde(default)]`, mirrors `skin: Option<String>` exactly).
- **`Vertex`/`SkinnedVertex` gain an unconditional `tangent: [f32; 4]` field** (xyz + handedness sign in w), always present in the GPU vertex format even for meshes with no stored `TangentData` (falls back to a documented dummy value, e.g. `[1.0, 0.0, 0.0, 1.0]`) — avoids a combinatorial explosion of tangent/no-tangent pipeline variants on top of the already-separate plain/skinned split.
- **Tangent generation: read glTF's `TANGENT` accessor when present, otherwise generate on import**, never at render time. `engine_assets::tangent::generate(positions, normals, uvs, indices)` implements the standard per-triangle-accumulate-then-average-then-Gram-Schmidt-orthogonalize algorithm (Lengyel/MikkTSpace-lite), run only when the imported material has a normal map assigned (no point computing tangents nobody will sample). Confirmed neither `tools/asset-gen/generate_crate.py` nor `generate_humanoid.py` currently pass `export_tangents=True` to Blender's `bpy.ops.export_scene.gltf` — both get that flag added as part of Phase 3, but the CPU-side generator remains the robust default regardless, since hand-authored/externally-sourced glTF (the actual bulk of real content per ADR-0009) can't be relied on to have it either way.
- **Lights: `Light` component with an explicit `direction: Vec3` for directional lights (not derived from `Transform.rotation`)**, mirroring `Camera.target`'s existing "explicit is easier to hand-author than a quaternion" reasoning; `Transform.rotation` stays unused on light entities exactly as it already is on the camera. Point lights use the entity's `Transform.position`. Spot lights are out of scope — no concrete consumer needs one yet, and the tier doc only names point/spot as "doesn't exist at all," not "both required now."
- **Zero-`Light`-entities scenes stay lit, not pitch black.** `extract_scene` synthesizes exactly one fallback directional light (the old hardcoded direction/color/intensity) when no `Light` entity exists in the scene, so every existing scene file (which authors none today) keeps rendering without any required authoring change. Rejected: requiring at least one authored `Light` — would silently turn every pre-existing scene fully black with no structural error to catch it, strictly worse than today.
- **Light-count and shadow-caster-count ambiguity are structured errors, not silent truncation/picking.** More than 4 `Light` entities in a scene is `RenderError::TooManyLights` (`RENDER_TOO_MANY_LIGHTS`); more than one `Light` with `casts_shadow: true` is `RenderError::MultipleShadowCasters` (`RENDER_MULTIPLE_SHADOW_CASTERS`); a non-directional light with `casts_shadow: true` is `RenderError::UnsupportedShadowCaster` (`RENDER_UNSUPPORTED_SHADOW_CASTER`). Matches `extract_scene`'s existing `NoCamera`/`MultipleCameras` precedent exactly (`crates/engine-render/src/error.rs`) — every new variant needs both an `#[error(...)]` message and a `.code()` match arm, same as every existing one.
- **Shadow mapping: exactly one directional shadow-casting light, a fixed-extent orthographic volume centered on the main camera's `target`, a single 2048×2048 `Depth32Float` map, no cascades.** Point-light shadows (cubemaps, 6 passes) and frustum/scene-bounds-fitted or cascaded shadow volumes are real quality gaps, left open on purpose — no concrete scene needs them yet, and a first working shadow pass is the actual goal here, not a general-purpose shadow system.
- **Per-frame uniform-buffer/bind-group pooling (`known-issues.md`'s deferred debt item) gets its own phase in this arc, not deferred again.** `known-issues.md` explicitly names Tier 2/3's fourth render pass (shadows) as the pre-declared trigger to revisit this — that pass lands in Phase 5 of this very arc, and it *doubles* the per-drawable fresh-buffer-and-bind-group cost the debt item already flags (every shadow-casting drawable is now drawn, and gets a fresh `Uniforms` buffer+bind group, in *two* passes per frame instead of one). Doing it as its own phase (6), after shadows land and before docs closeout, keeps "the shadow pass is visually correct" and "now make the whole draw path cheap" as separate, individually reviewable commits — matching this project's one-concern-per-phase discipline. It deliberately does **not** add a perf benchmark (none exists to validate against, same caveat `debt-cleanup-plan.md`'s Phase 4 already noted) — verification is existing golden-image tests staying byte-identical, since this is a pure allocation-pattern refactor with no intended visual change.

**Recommended order**: **1 → 2 → 3 → 4 → 5 → 6 → 7** — PBR base, then its texture import, then normal mapping (Phases 1-3 all touch `Material`/`shader.wgsl`/`skinned_shader.wgsl`/`texture_bind_group_layout` in immediate succession, per the tier doc's own "pair naturally" note), then multi-light (needs Phase 1's BRDF to loop over), then shadows (needs Phase 4's `Light` component to pick a caster — the tier doc's own stated reason to sequence it last among the four), then pooling (needs Phase 5 to make its cost concrete), then docs closeout. Order is load-bearing between 1→2→3 (each extends what the previous added) and 4→5 (5 needs `Light`); 6 could technically land earlier without breaking anything, but doing it last-before-docs is the reasonable default, not a hard requirement.

## Phase 1 — PBR material model, no textures yet

`crates/engine-render/src/components.rs`: `Material` gains `#[serde(default = "default_roughness")] roughness: f32` (default `1.0`) and `#[serde(default)] metallic: f32` (default `0.0`); update its doc comment (currently states "Full PBR is not a goal" — no longer true). `gpu.rs`'s private `Uniforms` struct gains a `material: [f32; 4]` field (`[roughness, metallic, 0.0, 0.0]`, padding kept explicit rather than repurposing `color`'s unused alpha channel) — populated in `draw()`'s per-drawable loop alongside `color`/`model`. `Drawable` (`gpu.rs`) gains `roughness: f32`/`metallic: f32`, filled from `Material` in `extract_scene`.

`shader.wgsl` and `skinned_shader.wgsl` both get their `fs_main` rewritten from the current Lambertian-plus-ambient block to the Cook-Torrance GGX / Schlick-Fresnel / Smith-visibility formulation against the single existing hardcoded `light_dir` (still a `Uniforms` field at this point — Phase 4 removes it once real `Light` entities replace it). Both files stay duplicated verbatim exactly as they already are (no WGSL include mechanism exists) — this phase touches both identically, same as every prior shader change.

New tests: a `crates/engine-render` unit test (or a small `#[cfg(test)]` block near `Uniforms`) round-tripping `Material`'s new fields through serde with the old two-field TOML shape still parsing (no `roughness`/`metallic` keys present) and getting the documented defaults. Regenerate every existing golden PNG this phase touches (`render_basic.golden.png`, `render_imported.golden.png`, `render_animation.golden.png` — `render_text.golden.png` is untouched, the UI pass has no lighting) via `cargo run -p engine -- render <scene> --to <path>`, reviewed visually before committing — the BRDF change alone shifts every lit pixel, unavoidably, and every phase from here through Phase 5 will need this same regeneration step.

**Verify**: full gate, golden PNGs regenerated and visually reviewed.

## Phase 2 — Metallic-roughness texture import + sampling

`crates/engine-assets/src/gltf_import.rs`: read `pbr.metallic_factor()`/`pbr.roughness_factor()` into `ImportedAsset` (replacing/joining the existing hardcoded factor-only base color read), and `pbr.metallic_roughness_texture()` — same `texture::Info` shape as `base_color_texture()`, so it goes through the existing `store_embedded_image` plumbing unchanged. `ImportedAsset` gains `roughness: f32`, `metallic: f32`, `metallic_roughness_texture_hash: Option<String>`.

`crates/engine-render/src/components.rs`: `Material` gains `#[serde(default)] metallic_roughness_texture: Option<String>`.

`gpu.rs`: `texture_bind_group_layout` grows a third entry (`binding: 2`, same `TextureSampleType::Float { filterable: true }` shape as base color, fragment-only) for the metallic-roughness texture, reusing the *existing* single sampler at `binding: 1` — no new sampler needed. Per glTF convention, roughness = G channel, metallic = B channel; the shader multiplies the per-drawable `material.x`/`material.y` uniform scalars by the sampled `g`/`b` (so an untextured or partially-textured material is unaffected — the scalar factor alone already carries the correct default when no texture is bound). The **existing shared `white_bind_group`'s white view already works as the default/identity texture for this slot** (white = `(1,1,1,1)`, so `g = b = 1.0`, a no-op multiplier) — no new default texture asset is needed here.

Because a material can now reference up to two independent texture hashes, `texture_cache`'s key changes from `String` to `(Option<String>, Option<String>)` (base color hash, metallic-roughness hash) — a bind group is cached per unique *combination*, not per single hash. `CACHE_CAPACITY` (256) is unchanged. `load_texture_bind_group`/`create_white_texture_bind_group` (`gpu.rs`) both grow a parameter for the second texture (each falling back to the shared white view when its own hash is `None`).

New tests: an `engine-assets` fixture glTF with a metallic-roughness texture (extend or add alongside the existing `crates/engine-assets/tests/fixtures/skinned.gltf`-style fixtures) proving `import_gltf` reads and stores it; a `texture_cache` unit/integration test proving two materials sharing a base-color hash but differing metallic-roughness hashes produce two distinct cached bind groups, not a collision. New golden fixture scene+PNG (`render_pbr_texture.golden.png`) with a textured, visibly-rough vs. visibly-metallic pair of cubes.

**Verify**: full gate, golden PNGs regenerated and visually reviewed.

## Phase 3 — Normal mapping (tangent generation + vertex format + normal-texture sampling)

`crates/engine-assets/src/tangent.rs` (new, mirrors `skin.rs`/`skeleton.rs` exactly): `TangentData { tangents: Vec<[f32; 4]> }`, `encode`/`decode` via `bincode` (own `AssetError::Tangent{Enc,Dec}odeFailed` variants), plus `generate(positions: &[[f32;3]], normals: &[[f32;3]], uvs: &[[f32;2]], indices: &[u32]) -> Vec<[f32;4]>` — per-triangle tangent/bitangent accumulation from edge/UV deltas, per-vertex averaging, Gram-Schmidt orthogonalization against the vertex normal, handedness sign from `sign(dot(cross(normal, tangent), bitangent))`. Unit tests: a hand-built single-triangle case with known UVs verifies the tangent points along the expected UV-U direction; a degenerate (zero-area or zero-UV-area) triangle doesn't panic or produce NaN (falls back to an arbitrary orthogonal tangent).

`crates/engine-assets/src/gltf_import.rs`: `material.normal_texture()` read (its own `NormalTexture` struct — `.texture()` for the image via the existing `store_embedded_image` path, `.scale()` stored alongside). Tangents: call `reader.read_tangents()` first; if `None` **and** a normal map is present, call `tangent::generate(...)`; store via `tangent::encode` and add `tangent_hash: Option<String>` to `ImportedAsset` — `None` when no normal map is assigned at all (no point generating/storing unused data). `store.put`'s content-addressing means re-importing an unchanged file still produces zero new/changed files, matching ADR-0005's existing guarantee.

`crates/engine-render/src/mesh.rs`: `Vertex`/`SkinnedVertex` both gain `tangent: [f32; 4]`, unconditionally present. `from_asset`/`from_skinned_asset` both gain an `Option<&engine_assets::tangent::TangentData>` parameter, filling the real tangent when present or a documented dummy (`[1.0, 0.0, 0.0, 1.0]`) when absent — same graceful-fallback posture `Drawable`'s doc comment already establishes for "skin present, no `JointPalette` yet." `gpu.rs`'s `vertex_layout()`/`skinned_vertex_layout()` both grow a fourth (fifth, for skinned) hand-computed `wgpu::VertexAttribute` (`Float32x4`) at the appropriate trailing offset, following the file's existing "no `vertex_attr_array!`, hand-listed offsets" convention exactly. `MeshRef` (`components.rs`) gains `#[serde(default)] tangent: Option<String>`; `load_mesh_buffers`/`load_skinned_mesh_buffers` (`gpu.rs`) both grow a tangent-hash parameter, decoding via `tangent::decode` when present.

`Material` gains `#[serde(default)] normal_texture: Option<String>` (plus the imported `.scale()` factor as a new `Material.normal_scale: f32`, default `1.0`). `texture_bind_group_layout` grows a fourth entry (`binding: 3`) for the normal map, reusing the same shared sampler. Since white `(1,1,1)` is **not** a valid default tangent-space normal, add one new shared 1×1 "flat normal" texture/view — `(128, 128, 255, 255)`, decoding to tangent-space `(0, 0, 1)` — alongside the existing white one, used as this slot's fallback in both `create_white_texture_bind_group`/`load_texture_bind_group`. `texture_cache`'s key grows to `(Option<String>, Option<String>, Option<String>)` (base, metallic-roughness, normal).

`shader.wgsl`/`skinned_shader.wgsl`: `VertexInput`/`VertexOutput` gain the tangent location; `vs_main` transforms tangent to world space alongside the normal; `fs_main` builds a TBN matrix (`bitangent = cross(normal, tangent.xyz) * tangent.w`), samples the normal map, remaps `[0,1] → [-1,1]`, scales `.xy` by `normal_scale`, transforms into world space via TBN, and feeds that (instead of the raw geometric normal) into Phase 1's BRDF.

Also update `tools/asset-gen/generate_crate.py`/`generate_humanoid.py`'s `bpy.ops.export_scene.gltf(...)` calls to pass `export_tangents=True` — confirmed neither passes it today; cheap and strictly better regardless of whether the CPU-side generator above ends up doing the real work for either script's actual mesh.

New golden fixture (`render_normal_map.golden.png`) with a normal-mapped surface under raking light, chosen so the bump pattern is visibly obvious.

**Verify**: full gate, golden PNGs regenerated and visually reviewed.

## Phase 4 — `Light` component + multi-light shader loop

`crates/engine-render/src/components.rs` (new types, alongside `Camera`/`Material`): `LightKind { Directional { direction: Vec3 }, Point { range: f32 } }` and `Light { kind: LightKind, color: [f32; 3], intensity: f32 }`. Registered via the existing 3-step recipe in `crates/engine-cli/src/registry.rs` (`impl Named for Light`, `registry.register("Light", load::<Light>, dump::<Light>)`), mirroring `Material`'s existing entry exactly. `Light` is always queried alongside `Transform` (`(&Transform, &Light)`, matching `Camera`'s own shape) — `Point`'s position comes from `Transform.position`; `Directional`'s explicit `direction` field means `Transform.rotation`/`.position` are simply unused on that entity, the same relationship `Camera.target` already has with its own `Transform.rotation`.

`gpu.rs`: new `GpuLight` (two `vec4<f32>`-shaped fields: position-or-direction + a w-tag, color + intensity — 32 bytes, inherently 16-byte-strided) and a `Lights { lights: [GpuLight; MAX_LIGHTS], count: u32, _pad: [u32; 3] }` uniform struct, `const MAX_LIGHTS: usize = 4`. New `lights_bind_group_layout` (one `uniform` buffer entry, fragment-only visibility) and a new `lights_bind_group` built **once per `draw()` call** (not per drawable — the first genuinely per-frame-not-per-drawable buffer in this file, a partial, natural step toward closing the known-issues.md pooling gap that Phase 6 finishes). `pipeline_layout`/`skinned_pipeline_layout` both grow to include it (main: `[uniform, texture, lights]`, 3 groups; skinned: `[uniform, texture, joint, lights]`, 4 groups — confirmed at, not over, wgpu 30's real `max_bind_groups: 4` default).

`extract_scene`: collects `Light` entities the same deterministic way cameras/drawables already are (`sort_by_key(|(e, _, _)| e.to_bits())`), erroring `RenderError::TooManyLights(usize)` (`.code()` = `RENDER_TOO_MANY_LIGHTS`) if more than `MAX_LIGHTS`. When zero `Light` entities exist, synthesizes one fallback directional light matching today's old hardcoded `LIGHT_DIR`/implicit white/`0.85`-scale values, so every scene file predating this phase keeps rendering unchanged (still needs golden PNG regeneration for the BRDF-loop restructuring itself, but not for missing content).

`shader.wgsl`/`skinned_shader.wgsl`: `Uniforms.light_dir` field is **removed** (no scene-file/serialization compatibility concern — `Uniforms` is a private, GPU-only struct, never scene-authored); `fs_main` loops `for (var i = 0u; i < lights.count; i++)` accumulating each light's BRDF contribution (directional: fixed direction; point: `normalize(light.position - world_pos)` with a simple inverse-square-with-range falloff) on top of Phase 1's per-light shading function, plus the existing flat ambient term once.

New tests: `extract_scene` unit coverage for the zero-light fallback, the `TooManyLights` error path, and deterministic ordering. New golden fixture (`render_multi_light.golden.png`) with two colored point lights plus one directional light visibly distinguishable on a simple scene.

**Verify**: full gate, golden PNGs regenerated and visually reviewed.

## Phase 5 — Shadow map render pass

`Light` (`components.rs`) gains `#[serde(default)] casts_shadow: bool`. `extract_scene` validates: more than one `casts_shadow: true` light is `RenderError::MultipleShadowCasters(usize)` (`.code()` = `RENDER_MULTIPLE_SHADOW_CASTERS`); a `casts_shadow: true` light whose `kind` isn't `Directional` is `RenderError::UnsupportedShadowCaster` (`.code()` = `RENDER_UNSUPPORTED_SHADOW_CASTER`) — matching `NoCamera`/`MultipleCameras`'s existing precedent (point-light shadows are out of scope — cubemap/6-pass cost with no concrete consumer yet).

New `shadow_shader.wgsl`: two `@vertex` entry points (`vs_main`, `vs_main_skinned` — mirroring the plain/skinned split, sharing one file since a depth-only pass needs no fragment stage at all, confirmed valid via wgpu 30's `RenderPipelineDescriptor.fragment: Option<FragmentState>` — `None` is legal with no color attachments). Both only read `position` (and, for the skinned entry, `joints`/`weights` to skin it) from the same vertex buffers the main pass already uploads — no separate shadow-specific mesh upload.

`gpu.rs` gains a new, deliberately separate `build_shadow_pipeline(device, label, layout, shader, entry_point, vertex_buffer_layout, bias: wgpu::DepthBiasState) -> wgpu::RenderPipeline` helper (not an extension of the existing `build_pipeline` — that function already hardcodes "always has a fragment/color target" and is at 9 params; forcing a depth-only shadow pipeline through it would mean several dead parameters). `RenderContext` gains: `shadow_pipeline`/`skinned_shadow_pipeline` (built once, not per-format — a shadow pass has no color-target format dependency, unlike `pipelines`/`skinned_pipelines`' `HashMap<TextureFormat, _>` shape), `shadow_pipeline_layout = [&bind_group_layout]` (reuses the *existing* per-drawable `Uniforms` bind group layout as-is — same struct shape, just filled with the light-space `view_proj` instead of the camera's at record time, no new layout needed), `skinned_shadow_pipeline_layout = [&bind_group_layout, &joint_bind_group_layout]` (group indices are local to this layout; no texture group needed for a depth-only pass), `shadow_map` (a `Depth32Float` texture, `RENDER_ATTACHMENT | TEXTURE_BINDING` — confirmed a guaranteed-valid combination for this format, no extra device feature required — recreated per-frame like `make_depth_view` already does for the main depth buffer), `const SHADOW_MAP_SIZE: u32 = 2048`, and `shadow_sampler` (`compare: Some(wgpu::CompareFunction::LessEqual)`, `SamplerBindingType::Comparison`).

`lights_bind_group_layout` (from Phase 4) grows two more entries: the shadow map (`texture_depth_2d`, `TextureSampleType::Depth`) and the comparison sampler; the `Lights` uniform struct grows `shadow_view_proj: mat4x4<f32>` and `shadow_caster_index: i32` (`-1` when no shadow caster exists) — reusing the *same* per-frame "lighting" buffer/bind group rather than adding a third one, per this plan's up-front design decision.

`draw()` (`gpu.rs`) records a **new first render pass** in the same encoder, before the existing main pass: `color_attachments: &[]`, `depth_stencil_attachment` targeting `shadow_map`, drawing every non-text drawable (all drawables cast shadows unconditionally — no per-object opt-out yet, no concrete need for one) with the shadow pipeline(s), each filled with a per-drawable `Uniforms` buffer whose `view_proj` is the light-space matrix instead of the camera's. Light-space `view_proj`: an orthographic projection with a fixed half-extent (new consts `SHADOW_ORTHO_HALF_EXTENT`, `SHADOW_NEAR`, `SHADOW_FAR`) centered on the main camera's `target` — not scene-bounds-fitted or cascaded, a deliberate, named scoping limit.

`shader.wgsl`/`skinned_shader.wgsl`: `vs_main` computes `shadow_clip_position = lights.shadow_view_proj * world_pos` as a new `VertexOutput` field; `fs_main`, only for the light at `lights.shadow_caster_index` (skipped entirely when `-1`), converts to shadow-map UV (`shadow_clip.xy * vec2(0.5, -0.5) + 0.5`, wgpu's clip-space Y convention) and calls `textureSampleCompare(shadow_map, shadow_sampler, uv, ref_depth - SHADOW_BIAS)`, multiplying that light's own diffuse+specular contribution by the resulting `[0,1]` visibility factor.

New tests: an `extract_scene` unit test each for `MultipleShadowCasters`/`UnsupportedShadowCaster`. New golden fixture (`render_shadow.golden.png`) — a cube and a ground plane under one shadow-casting directional light, framed so the cube's shadow visibly lands on the ground plane.

**Verify**: full gate, golden PNGs regenerated and visually reviewed.

## Phase 6 — Per-frame uniform-buffer/bind-group pooling

Closes `known-issues.md`'s "`draw()` allocates a fresh uniform buffer + bind group per drawable every frame" item, whose own text names this exact pass (shadows, landed in Phase 5) as the revisit trigger. `RenderContext` gains a persistent per-entity pool for the per-drawable `Uniforms` buffer+bind-group (`HashMap<hecs::Entity, (wgpu::Buffer, wgpu::BindGroup)>`, keyed the same way `extract_scene`'s existing deterministic entity sort already identifies drawables) and an equivalent pool for skinned drawables' joint-matrix buffer+bind-group. Each frame, an existing pool entry is updated in place via `queue.write_buffer` instead of `create_buffer_init`; a new entity's slot is created once; entities no longer present in the current frame's drawable set are evicted — mirroring `engine-physics`'s existing `PhysicsState::evict_despawned` pattern in spirit. The Phase 4 `lights_bind_group`'s single per-frame buffer also switches from fresh `create_buffer_init` to a persisted buffer updated via `write_buffer`, for the same reason.

This only meaningfully pays off for the live/windowed path (`draw_to_surface`, called every frame with a stable entity set across frames) — `render_scene`/`render_scene_with_context`'s one-shot/batch callers never get a "next frame" to amortize across, so the pool is harmless-but-inert there, not actively exploited. Worth stating plainly rather than silently.

No visual change is intended — this is a pure allocation-pattern refactor.

**Verify**: golden-image tests must stay byte-identical/within-tolerance unchanged (no regeneration this phase, unlike every prior one). Full gate.
