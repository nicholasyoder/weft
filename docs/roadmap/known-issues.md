# Known issues & engineering debt

> **This is a different kind of list than the tier files.** Tiers 1–4 track *capabilities the engine doesn't have yet*. This file tracks *places where the code doesn't do what its own docs/tests/design already claim it does*, plus architectural debt that's cheap to fix now and expensive to fix once more is built on top of it. Found by a full critical review on 2026-09-02 (source code + ADRs + roadmap, four parallel audits — core/scene/physics/anim, render/assets/audio, scripting/CLI/MCP, sandbox+docs+tooling). Same rule as the rest of this roadmap applies: this is a living list, not a queue — pull whatever's actually biting, update this file as items get fixed or superseded.

## Critical — contradicts a stated guarantee today

**All three items below are fixed (2026-09-02).** Kept here, marked fixed, rather than deleted — the review found them, this file is the historical record of what "critical" meant on this pass, and each links to the ADR/commit-worthy detail of how it was actually closed.

### ~~Lua sandbox does not actually sandbox scripts~~ — fixed
`crates/engine-script/src/host.rs:30` created the Lua VM with `StdLib::ALL_SAFE`. Checked directly against mlua 0.12.1's own source (`stdlib.rs`): `ALL_SAFE = (1<<30)-1`, which **included** the `IO`, `OS`, and `PACKAGE` bits — mlua's "safe" means "no `debug`/`ffi`," not "no filesystem/process." Every script's private `_ENV` (added in the Phase-10 follow-up) fell through to real globals for anything it didn't locally define, so any loaded `.lua` script had working `io.open`, `os.execute`, `os.getenv`, `os.remove`, `require`. **[ADR-0006](../decisions/0006-scripting-and-hot-reload.md)'s Decision 4 stated as fact that "`ALL_SAFE` already excludes `io`/`os`/`debug`/`ffi`" — that line was factually wrong.** Fixed by switching to an explicit allowlist (`COROUTINE | TABLE | STRING | UTF8 | MATH`, `crates/engine-script/src/host.rs`'s `sandbox_stdlib()`) — `io`/`os`/`package`/`debug`/`ffi` are now all excluded. `coroutine` was added proactively (nothing used it yet) since it's a pure-language feature useful for future cutscene/dialogue-sequencing scripts, at zero security cost. Regression tests in `crates/engine-script/tests/host.rs` (`io_os_and_package_are_not_reachable_from_scripts`, `coroutines_are_usable_inside_a_script`) cover both directions. ADR-0006 itself is updated in place with the correction and the fix.

### ~~Animation-clip content hashing is nondeterministic~~ — fixed
`crates/engine-assets/src/gltf_import.rs` built `AnimationClip.tracks` from a `HashMap<u16, JointTrack>` via `.into_values().collect()` with **no sort** before the struct was bincode-encoded and hashed. Rust's default `HashMap` iteration order is randomized per process, so re-importing the *same* glTF file twice could produce two different content hashes — directly breaking the guarantee [ADR-0005](../decisions/0005-asset-pipeline.md)/[ADR-0015](../decisions/0015-animation-data-pipeline.md) build the whole content-addressed store around. Fixed: tracks are now sorted by joint index (`tracks_sorted_by_joint`) before collecting into the `Vec` the struct actually needs — `engine-anim::sampling::sample` already looked tracks up by joint field regardless of order, so this changes nothing about playback. Covered by a unit test asserting the sort invariant directly (order-independent of `HashMap`'s actual iteration behavior) plus an integration-level "import twice, same hash" test in `crates/engine-assets/tests/import.rs`.

### ~~Systems have no error channel — bad content data panics the whole process~~ — fixed
`System = fn(&mut SystemArgs)` (`engine-core/src/scheduler.rs`) returned nothing fallible. `engine-anim`'s `ensure_skeleton`/`ensure_clip` and `engine-audio`'s `ensure_clip` both `panic!`ed on an unresolvable or corrupt asset hash — a single bad `Animator.clip` or `AudioSource.clip` string in a scene file could crash `run`/`render`/`mix`/`play` outright with no structured `CliError`. Fixed: `System` now returns `Result<(), SystemError>`; `Scheduler`/`Sim` propagate a failing system's name and error up to `engine-cli`, which converts it into the same `{code, message, context}` envelope every other failure uses (`CliError::from_system_error`). Both real panics were fixed by reusing existing error types (`AssetError`, plus one new `AudioError::ClipDecodeFailed` variant) rather than inventing new machinery. Verified directly: `engine test --scene <bad-clip-hash> --format json` now exits 1 with `{"error": {"code": "ASSET_NOT_FOUND", "context": {"system": "animation", "tick": 0}, ...}}` instead of a Rust panic/backtrace. Full design in [ADR-0017](../decisions/0017-system-error-channel.md).

## Real bugs

- ~~**`engine mix` and `engine play` can diverge for the same scene.**~~ — fixed 2026-09-02: the offline `Mixdown` had no per-voice handle, so despawn-eviction had nothing to stop when a looping `AudioSource`'s entity despawned — it kept rendering in `mix` but stopped in live `play`. `Mixdown` voices now get an id (`play()` returns it) and a `stop_voice(id)`; `AudioBackend::play_source` returns a `VoiceHandle` (`Live`/`Mix`) for either backend so `AudioCache::evict_despawned` can stop either one the same way.
- ~~**Multi-script dispatch errors are collected, then thrown away.**~~ — fixed 2026-09-02: `step_and_dispatch_with_input` kept only the first of `ScriptHost::dispatch`'s per-entity errors (`errors.into_iter().next()`). `CliError::from_script_errors` now keeps the first error's `code`/`message` (unchanged single-error behavior) but lists every error in `context.errors` instead of dropping the rest.
- ~~**`engine-render/src/mesh.rs:143-147` used `assert_eq!` (panics) on a mesh/skin vertex-count mismatch**~~ — fixed 2026-09-02: `from_skinned_asset` now returns `RenderError::SkinVertexCountMismatch`, propagated through `load_skinned_mesh_buffers`'s existing `?` chain like every other decode path in the crate.
- ~~**`Mixdown::render` had no carried fractional remainder between ticks**~~ — fixed 2026-09-02: at rates that don't evenly divide (8000Hz @ 60Hz, the repo's own golden-WAV fixture rate), frame counts drifted from `ticks * dt` over a long run. `Mixdown` now carries a `frame_accum` remainder across calls, `floor()`'d each call (with a small epsilon absorbing `dt`'s own f32→f64 promotion error) instead of rounded independently each time. The golden WAV fixture was regenerated since its frame schedule legitimately changed.
- ~~**`--watch`'s file debouncer was torn down for the entire duration of every rerun**~~ — fixed 2026-09-02: the debouncer is now created once before the loop and never torn down; an edit landing during a rerun queues in the channel and is picked up on the next `recv()` once the rerun ends, instead of being silently missed.
- ~~**`AGENTS.md`'s "Live windowed play" section is stale**~~ — fixed 2026-09-02: it said `engine play` reads "WASD + Space + Escape," but Phase 11 generalized `KeyCode` to the full practical set (A–Z, digits, arrows, Enter/Tab, Shift/Control/Alt) — confirmed live-wired in `engine-cli/src/live.rs`'s `map_key`. Corrected in place.
- **`README.md` and `ROADMAP.md` were stale by three shipped phases** as of this review (fixed alongside it 2026-09-02) — both still described "no audio, no animation, no text/UI" as open gaps after Phases 12–14 shipped all three and closed Tier 1. `docs/roadmap/completed-phases.md` and `AGENTS.md`'s operation table were current throughout; only the two root-level entry-point docs drifted.
- ~~**`engine play`/`cargo run -p sandbox` never produced any audio or animation, on any machine, regardless of device availability.**~~ — fixed 2026-09-02: `engine_cli::live::play` opened a real audio device (`LiveAudioBackend::new()`) but never inserted `engine_core::AssetsDir` into `Sim`'s `Resources` — the one thing `animation_step`/`audio_step` both require before doing anything (by design, see ADR-0015/ADR-0016's "missing `AssetsDir` is a silent no-op" convention). Every batch command (`test`/`inspect`/`run`/`replay`) gets this via `SimSource::build`; `live::play` had its own separate setup path that never got the same line. Found when the user ran `cargo run -p sandbox` for the first time on a real machine with a real audio device (Phase 8's new ambient loop) and heard nothing — every prior audio/live-input phase (10, 11, 14) had only been verified via crate-level dispatch tests or in this sandbox's own device-less environment, so a live session with a working device had never actually been listened to before. Fixed by inserting `AssetsDir` in `live::play`'s setup (now extracted into a `build()` helper, testable without a window/event loop — `crates/engine-cli/src/live.rs`'s `tests::assets_dir_is_inserted` asserts the resource is present, closing the actual regression gap: nothing previously would have caught this).

## Architectural debt worth addressing before it compounds

- **`Resources` (`engine-core/src/resources.rs`) is an `Option`-typed grab-bag** with no compile-time distinction between "always present" (e.g. `AudioSettings`) and "genuinely optional" (e.g. `AssetsDir`) resources — that distinction lives only in doc comments; deferred (a heavier required/optional struct split, not just an API addition — see `docs/roadmap/debt-cleanup-plan.md`'s "Not planned" scoping note). ~~No `remove`, so a resource inserted once lives for the `Sim`'s full lifetime.~~ — fixed 2026-09-02: `Resources::remove::<T>()` added.
- ~~**`engine-core` is accreting an unrelated "shared vocabulary" bag**~~ — fixed 2026-09-02: `Transform`, `JointPalette`, `AudioSettings`, `SoundEvent`/`SoundEventQueue`, `Input`/`KeyCode`, `AssetsDir` moved verbatim to a new leaf crate, `engine-types` (no dependency on `engine-core` or anything else in the workspace). `engine-core` now depends on `engine-types` and re-exports every item flat (`engine_core::Transform` etc. all still work unchanged — re-exports preserve `TypeId`, so this is behaviorally transparent to hecs component lookup and `Resources` keying) rather than every one of the ~9 downstream crates gaining a second, direct `engine-types` dependency: traced every actual usage first and found every file importing one of these types also imports a genuine `engine-core` kernel item (`Sim`, `SystemArgs`, `ComponentDumper`, `Resources`) in the same `use`, so a direct-dependency migration would've meant touching ~9 `Cargo.toml`s and ~20 files' imports for no real decoupling payoff today. The boundary this establishes is real regardless: `engine-core`'s own `Cargo.toml` no longer owns these type definitions (dropped its now-unused direct `glam` dependency in the process — confirmed via `cargo tree` it's now only pulled in transitively), and a genuinely leaf-only future producer/consumer pair could depend on `engine-types` alone. 3 unit tests that exercised `Resources` round-tripping (previously living alongside `AssetsDir`/`AudioSettings`/`SoundEventQueue`'s own definitions) moved to a new `crates/engine-core/tests/shared_types_via_resources.rs`, since the leaf crate can't depend on `Resources`.
- **The scenario/scene split is a widening seam, not a static one.** `SimSource::build` (`engine-cli/src/lib.rs:56-75`) manually re-inserts defaults (e.g. `AudioSettings::default()`) for the hardcoded-`Scenario` arm because it never goes through `engine_scene::load`. Every new scene-file-only feature needs a parallel manual patch to keep both paths equivalent. *(Corrected 2026-09-02: only 1 of 4 built-in scenarios — `broken-rng` — has no scene-file counterpart, not 2 as previously stated; that's by design, since `broken-rng` exists specifically to bypass the seeded RNG via `rand::thread_rng()` and can't be reproduced from a declarative scene file. `basic`/`physics-demo`/`despawn-demo` all have matching fixtures. The seam itself is unchanged by this correction — still open.)*
- ~~**`engine-render/src/gpu.rs` had three near-identical (~95%) `RenderPipelineDescriptor` blocks** (mesh/UI-text/skinned)~~ — fixed 2026-09-02: the three call sites (`pipeline_for`/`skinned_pipeline_for`/`ui_pipeline_for`) now call one shared `build_pipeline` free function, parameterized by the 8 fields that actually varied (label, shader, layout, vertex buffer layout, blend, cull mode, depth-write, depth-compare); everything identical across all three (entry points, `compilation_options`, `write_mask`, `topology`/`front_face`, `depth_stencil.format`, `stencil`/`bias`/`multisample`/`multiview_mask`/`cache`) now lives in one place. **`draw()` still allocates a fresh uniform buffer + bind group per drawable every frame, no pooling** — deliberately deferred (debt-cleanup-plan.md's Phase 4 scoping: no perf test exists to validate pooling against). Tier 2/3 both want a fourth pass (shadows) — the pipeline-builder dedup means that no longer means tripling the copy-paste; pooling itself stays open.
- ~~**Four-plus unbounded, insert-only caches with no eviction**: `mesh_cache`/`texture_cache`/`font_cache`/`skin_cache` on `RenderContext`, plus `engine-audio`'s clip cache.~~ — fixed 2026-09-02: all five converted from `HashMap` to `lru::LruCache` at a fixed 256-entry capacity (`CACHE_CAPACITY` in `engine-render/src/gpu.rs`, `CLIP_CACHE_CAPACITY` in `engine-audio/src/system.rs`). Every callsite already followed a check-then-load-if-missing-then-read pattern, so eviction only costs an occasional reload, never correctness. `engine-render`'s `pipelines`/`skinned_pipelines`/`ui_pipelines` (keyed by the tiny set of distinct `wgpu::TextureFormat`s actually used) and `engine-audio`'s `started` map (despawn-eviction tracking, not an asset cache) were left as plain `HashMap`s — out of scope.
- ~~**Determinism-by-sorting is enforced by convention only, and is already applied inconsistently.**~~ — fixed 2026-09-02: `engine-physics`'s despawn eviction sorts by entity id per ADR-0002/0011 (`system.rs:65-78`); the pose write-back loop 20 lines later now collects+sorts the same way before iterating, instead of iterating the unsorted `HashMap<Entity, RigidBodyHandle>` directly.
- ~~**Two semver-incompatible `glam` versions live in the dependency graph** (workspace pin vs. the version rapier3d pulls), requiring manual field-by-field conversion at every physics boundary call (`engine-physics/src/convert.rs`).~~ — fixed 2026-09-02: workspace `glam` pin bumped `0.29`→`0.33`, matching the `glam 0.33.6` already pulled transitively via `rapier3d`→`parry3d`/`glamx`. Turned out `rapier3d::math::Vector`/`Rotation` aren't `nalgebra` types at all — `glamx` (rapier3d's math backend) defines them as direct re-exports of `glam::Vec3`/`glam::Quat` — so once the pins matched, they became the literal same type, not just interconvertible. `engine-physics/src/convert.rs` deleted outright (not rewritten to `.into()` calls); its 6 call sites in `system.rs` now pass/read `glam::Vec3`/`Quat` values directly. Two now-deprecated glam camera fns (`Mat4::perspective_rh`/`Mat4::look_at_rh`, moved to `glam::camera::rh::proj::directx::perspective`/`glam::camera::rh::view::look_at_mat4` in the new version) were updated in `engine-render/src/gpu.rs` — same NDC convention, golden-image tests stayed byte-identical. The stale 0.30/0.31/0.32 lockfile `glam` copies (optional-feature pulls on `nalgebra`, independent of the workspace pin) remain — not chased further, since the real payoff (single glam version for all first-party code) didn't depend on it.
- ~~**Per-component `load_x`/`dump_x` boilerplate is hand-written with no macro**, duplicated between `engine-cli/src/registry.rs` and `games/sandbox/src/lib.rs`.~~ — fixed 2026-09-02: replaced the ~19 hand-written pairs (plus their reuse sites across `engine-cli/src/scenarios/*.rs`) with two generic functions, `load::<T>`/`dump::<T>` (`engine-cli/src/registry.rs`), keyed off a small local `Named` trait giving each component type its scene-file name. `games/sandbox/src/lib.rs`'s 3 pairs reuse the same two generics. No macro needed.
- **The error-handling convention has already forked.** `engine-scene`/`engine-script`/`engine-render`/`engine-audio`/`engine-assets` all implement a `.code()` method on a `thiserror` enum; `engine-physics` has no error type at all — genuinely infallible today, nothing to convert. *(Corrected 2026-09-02: `engine-anim` is not part of the same fork the way this bullet previously implied. It no longer panics — fixed by the earlier Critical-item work — but it gets there by converting a foreign `engine_assets::AssetError` into `engine_core::scheduler::SystemError` via a small local helper (`system.rs`'s `to_system_error`), not by owning a `thiserror`-based `Error` enum of its own: no `thiserror` dependency in its `Cargo.toml`, no `error.rs`. That's arguably a fine design on its own terms — it has no fallible operation of its own beyond asset lookup, so nothing to own an error type over — not a fixed instance of the five-crate `.code()` convention. Not architecturally changed by this correction, only the claim.)*
- ~~**`engine-core::SimError` (`error.rs`) is dead code**~~ — fixed 2026-09-02: deleted (`error.rs` and its `pub mod error;` in `lib.rs`) — confirmed zero references workspace-wide before removal.

## Process / testing gaps

- ~~**No CI exists anywhere in the repo**~~ — fixed 2026-09-02: `.github/workflows/ci.yml` runs on every push/PR to `main` (single Ubuntu job: `mesa-vulkan-drivers`/`libasound2-dev` installed, then `cargo test --workspace`/`clippy --all-targets -- -D warnings`/`fmt --all -- --check`, plus `pytest tools/asset-gen`). Still just single-platform (Linux) — tier-4's "CI build matrix" cross-platform item stays separately open.
- **`games/sandbox`, the only integration testbed, has zero coverage of animation or looping background music.** `playground.toml` has no skinned mesh, no `Animator`, no `[audio]` table — only one-shot `engine.play_sound` is exercised. Cross-subsystem interaction bugs (animation+physics, animation+rendering, looping audio+despawn) have no test surface anywhere in the repo. (The sandbox's *existing* tests are otherwise genuinely good — real assertions on exact state, not smoke tests — this is a coverage gap, not a quality one.)
- ~~**`tools/asset-gen/generate_crate.py` has zero automated test coverage.**~~ — fixed 2026-09-02: `tools/asset-gen/test_generate_crate.py` (pytest, run in CI) covers `parse_args()`'s defaults and `--color`/`--bevel-width` parsing, stubbing `bpy` in `sys.modules` before import since the module imports it at top level. `main()`'s actual Blender generation logic stays uncovered by design — still consistent with [ADR-0009](../decisions/0009-asset-generation-workflow.md)'s workspace-boundary call, since `bpy` only exists inside a real Blender install, not CI.
- ~~**MCP error-path test coverage is thin relative to the diagnostics surface.**~~ — fixed 2026-09-02: `engine-mcp/tests/tools.rs` now also covers `SIM_SOURCE_CONFLICT`, `INVALID_TICKS` on all five ticks-accepting tools, and one further error path each for `weft_replay`/`weft_render`/`weft_mix`/`weft_import` (`RECORDING_INVALID_SOURCE`, `RENDER_NO_CAMERA`, `SCENE_READ_ERROR`, `IMPORT_UNSUPPORTED_EXTENSION` respectively), reusing fixtures `engine-cli`'s own suite already established for each. Also added the probe for `rmcp`'s own pre-tool-body schema rejection (a call missing `RunParams.scene`) — **confirmed, not hypothetical: it fails loudly (`is_error: true`, a readable message) but does *not* go through `CliError`,** so it has no `structured_content` and no `error.code` at all, unlike every other failure in this codebase. Not fixed — genuinely fails loudly per AGENTS.md's core guarantee, just in a different, currently-undocumented shape than the `{error:{code,message,context}}` envelope this crate's own module doc comment claims is universal. Worth a follow-up (either wrap the schema-rejection path into the same envelope, or document the exception) but out of scope for a test-coverage pass.

## Positives worth naming (so they don't get lost in a list of problems)

- Determinism discipline has held almost everywhere it matters — the two real violations found (animation-clip hashing, the physics write-back loop's latent risk) are narrow and specific, not systemic.
- The CLI/MCP structured-error contract (`{code, message, context}`) is real and consistently applied across almost the entire surface — the gaps found are at the edges (panics in two systems, MCP schema-rejection path), not the common case.
- `docs/roadmap/completed-phases.md` and `AGENTS.md`'s operation table were both fully current through Phase 14 at review time — the staleness found was isolated to README.md/ROADMAP.md's higher-level framing, not the detailed records.
- `games/sandbox`'s existing tests assert real, specific behavior (exact positions, exact HUD strings, a regression test for a previously-shipped bug) rather than "it ran."
- Repo hygiene is clean: `Cargo.lock` tracked, `.gitignore` scoped tightly, no build artifacts accidentally committed.
