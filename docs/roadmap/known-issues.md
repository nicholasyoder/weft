# Known issues & engineering debt

> **This is a different kind of list than the tier files.** Tiers 1–4 track *capabilities the engine doesn't have yet*. This file tracks *places where the code doesn't do what its own docs/tests/design already claim it does*, plus architectural debt that's cheap to fix now and expensive to fix once more is built on top of it. Found by a full critical review on 2026-09-02 (source code + ADRs + roadmap, four parallel audits — core/scene/physics/anim, render/assets/audio, scripting/CLI/MCP, sandbox+docs+tooling). Same rule as the rest of this roadmap applies: this is a living list, not a queue — pull whatever's actually biting, update this file as items get fixed or superseded.

---

## Critical — contradicts a stated guarantee today

### Lua sandbox does not actually sandbox scripts
`crates/engine-script/src/host.rs:30` creates the Lua VM with `StdLib::ALL_SAFE`. Checked directly against mlua 0.12.1's own source (`stdlib.rs`): `ALL_SAFE = (1<<30)-1`, which **includes** the `IO`, `OS`, and `PACKAGE` bits — mlua's "safe" means "no `debug`/`ffi`," not "no filesystem/process." Every script's private `_ENV` (added in the Phase-10 follow-up) falls through to real globals for anything it doesn't locally define, so any loaded `.lua` script today has working `io.open`, `os.execute`, `os.getenv`, `os.remove`, `require`. **[ADR-0006](../decisions/0006-scripting-and-hot-reload.md)'s Decision 4 states as fact that "`ALL_SAFE` already excludes `io`/`os`/`debug`/`ffi`" — that line is factually wrong**, not just outdated; see the correction note added directly to that ADR. Fix direction: swap to an explicit allowlist (`TABLE | STRING | MATH | UTF8 | ...`) rather than a "safe minus a few" list, and add a regression test that asserts `io`/`os`/`package` are absent from a script's environment.

### Animation-clip content hashing is nondeterministic
`crates/engine-assets/src/gltf_import.rs:411` builds `AnimationClip.tracks` from a `HashMap<u16, JointTrack>` and does `.into_values().collect()` with **no sort** before the struct is bincode-encoded and hashed. Rust's default `HashMap` iteration order is randomized per process, so re-importing the *same* glTF file twice can produce two different content hashes — directly breaking the guarantee [ADR-0005](../decisions/0005-asset-pipeline.md)/[ADR-0015](../decisions/0015-animation-data-pipeline.md) build the whole content-addressed store around ("importing an unchanged file produces the same hash, zero diff churn"). Every other asset type in that crate (`mesh.rs`, `skin.rs`, `skeleton.rs`) is `Vec`-only and correctly deterministic — this is an isolated leak. Fix direction: sort tracks by joint index before collecting into the `Vec` the struct actually needs.

### Systems have no error channel — bad content data panics the whole process
`System = fn(&mut SystemArgs)` (`engine-core/src/scheduler.rs`) returns nothing fallible. `engine-anim`'s `ensure_skeleton`/`ensure_clip` (`system.rs:38-56`) and `engine-audio`'s `ensure_clip` (`system.rs:35-44`) both `panic!` on an unresolvable or corrupt asset hash — a single bad `Animator.clip` or `AudioSource.clip` string in a scene file crashes `run`/`render`/`mix`/`play` outright with no structured `CliError`, unlike every other failure mode in the engine. [ADR-0015](../decisions/0015-animation-data-pipeline.md) already flagged this gap for animation as a "revisit when"; it has since spread to audio with no design done. This is a structural limitation of the `System` type itself, not a per-crate oversight — worth deciding once (does `System` gain a `Result` return and a defined "what happens to the tick when a system errors" policy?) rather than papering over it crate by crate again.

## Real bugs

- **`engine mix` and `engine play` can diverge for the same scene.** The offline mixer's `AudioBackend::Mix::play_source` always returns `None` (`engine-audio/src/backend.rs:105-108`), so despawn-eviction has nothing to stop — a looping `AudioSource` on a despawned entity keeps rendering in `mix` but stops in live `play`.
- **Multi-script dispatch errors are collected, then thrown away.** `ScriptHost::dispatch` deliberately gathers *every* per-entity script error in a tick so one bad script doesn't hide another's failure (`host.rs:89-108`'s own doc comment) — but `engine-cli`'s `step_and_dispatch_with_input` (`lib.rs:161-164`) does `errors.into_iter().next()`, silently discarding all but the first.
- **`engine-render/src/mesh.rs:143-147`** uses `assert_eq!` (panics) on a mesh/skin vertex-count mismatch instead of returning `RenderError` like every other decode path in the crate.
- **`Mixdown::render` (`engine-audio/src/mixdown.rs:63-64`) has no carried fractional remainder** between ticks — when `sample_rate` isn't evenly divisible by tick rate (true of the repo's own golden-WAV fixture, 8000Hz @ 60Hz), frame counts drift from `ticks * dt` over a long run. Byte-identical across repeated runs (so the golden test can't catch it), but real timing drift.
- **`--watch`'s file debouncer is torn down for the entire duration of every rerun**, not just at startup (`engine-cli/src/watch.rs`: `drop(debouncer)` before the full rerun, a fresh one created only after). An edit landing mid-rerun is never observed. Gets worse as scenes/tick-budgets grow, since a rerun replays the whole `--ticks` budget from scratch — exactly when an edit is most likely to land in that window.
- **`AGENTS.md`'s "Live windowed play" section is stale**: it says `engine play` reads "WASD + Space + Escape," but Phase 11 generalized `KeyCode` to the full practical set (A–Z, digits, arrows, Enter/Tab, Shift/Control/Alt) — confirmed live-wired in `engine-cli/src/live.rs`'s `map_key`. Needs a one-line correction.
- **`README.md` and `ROADMAP.md` were stale by three shipped phases** as of this review (fixed alongside it 2026-09-02) — both still described "no audio, no animation, no text/UI" as open gaps after Phases 12–14 shipped all three and closed Tier 1. `docs/roadmap/completed-phases.md` and `AGENTS.md`'s operation table were current throughout; only the two root-level entry-point docs drifted.

## Architectural debt worth addressing before it compounds

- **`Resources` (`engine-core/src/resources.rs`) is an `Option`-typed grab-bag** with no compile-time distinction between "always present" (e.g. `AudioSettings`) and "genuinely optional" (e.g. `AssetsDir`) resources — that distinction lives only in doc comments. No `remove`, so a resource inserted once lives for the `Sim`'s full lifetime.
- **`engine-core` is accreting an unrelated "shared vocabulary" bag**: `Transform`, `JointPalette`, `AudioSettings`, `SoundEvent`/`SoundEventQueue`, `Input`/`KeyCode`, `AssetsDir` all live there purely so producer/consumer crate pairs avoid a direct dependency. Each addition is individually justified (ADR-0015's reasoning), but there's no boundary rule stopping this from becoming a junk drawer as more crate pairs want a shared type.
- **The scenario/scene split is a widening seam, not a static one.** `SimSource::build` (`engine-cli/src/lib.rs:56-75`) manually re-inserts defaults (e.g. `AudioSettings::default()`) for the hardcoded-`Scenario` arm because it never goes through `engine_scene::load`. Every new scene-file-only feature needs a parallel manual patch to keep both paths equivalent, and 2 of 4 built-in scenarios have no scene-file counterpart at all.
- **`engine-render/src/gpu.rs` is ~1330 lines with three near-identical (~95%) `RenderPipelineDescriptor` blocks** (mesh/UI-text/skinned), and `draw()` allocates a fresh uniform buffer + bind group per drawable *every frame*, no pooling. Tier 2/3 both want a fourth pass (shadows) — worth extracting a shared pipeline-builder before that lands rather than tripling the copy-paste again.
- **Four-plus unbounded, insert-only caches with no eviction**: `mesh_cache`/`texture_cache`/`font_cache`/`skin_cache` on `RenderContext`, plus `engine-audio`'s clip cache. Fine for short batch commands; a real leak risk in a long-running `engine play` session with hot-reloaded/regenerated assets. No design exists yet for eviction (LRU, explicit invalidation, or otherwise).
- **Determinism-by-sorting is enforced by convention only, and is already applied inconsistently.** `engine-physics`'s despawn eviction sorts by entity id per ADR-0002/0011 (`system.rs:65-78`), but the pose write-back loop 20 lines later iterates an unsorted `HashMap<Entity, RigidBodyHandle>` (harmless today only because each entity's read/write is independent — the next person adding cross-entity logic to that loop has no signal they've broken determinism).
- **Two semver-incompatible `glam` versions live in the dependency graph** (workspace pin vs. the version rapier3d pulls), requiring manual field-by-field conversion at every physics boundary call (`engine-physics/src/convert.rs`). Correct today; an easy spot for a silent bug if either pin drifts independently.
- **Per-component `load_x`/`dump_x` boilerplate is hand-written with no macro**, duplicated between `engine-cli/src/registry.rs` and `games/sandbox/src/lib.rs`. A second real game inherits this ~10-line-per-component tax from scratch. Worth a derive macro or generic serde-based registration helper once a second game makes the duplication concrete rather than hypothetical.
- **The error-handling convention has already forked.** `engine-scene`/`engine-script`/`engine-render`/`engine-audio`/`engine-assets` all implement a `.code()` method on a `thiserror` enum; `engine-physics` has no error type at all and `engine-anim` doesn't depend on `thiserror` — both panic instead (see the Critical item above). One convention, two populations.
- **`engine-core::SimError` (`error.rs`) is dead code** — an empty enum, never constructed anywhere. Cargo-culted from the "every crate gets an error.rs" convention with no actual fallible operation behind it yet. Either give it a real variant when one exists, or delete it.

## Process / testing gaps

- **No CI exists anywhere in the repo** (no `.github/`, no `.gitlab-ci.yml`, nothing) — confirmed directly, not inferred from tier-4's "CI build matrix" item (which is about *cross-platform* coverage; this is plainer: there's zero automated enforcement of `cargo test`/`clippy -D warnings`/`fmt --check`, even single-platform, on every push). Everything AGENTS.md calls a hard gate is enforced by agent discipline alone today.
- **`games/sandbox`, the only integration testbed, has zero coverage of animation or looping background music.** `playground.toml` has no skinned mesh, no `Animator`, no `[audio]` table — only one-shot `engine.play_sound` is exercised. Cross-subsystem interaction bugs (animation+physics, animation+rendering, looping audio+despawn) have no test surface anywhere in the repo. (The sandbox's *existing* tests are otherwise genuinely good — real assertions on exact state, not smoke tests — this is a coverage gap, not a quality one.)
- **`tools/asset-gen/generate_crate.py` has zero automated test coverage.** Deliberately outside the Cargo workspace per [ADR-0009](../decisions/0009-asset-generation-workflow.md), which is a defensible boundary call, but it leaves the one deterministic content-generation script in a "deterministic asset pipeline" project with no regression protection if it's ever edited.
- **MCP error-path test coverage is thin relative to the diagnostics surface.** `engine-mcp/tests/tools.rs` exercises exactly two error codes (`SCENE_READ_ERROR`, `SCENARIO_NOT_FOUND`) across all seven tools. Untested: `weft_replay`/`weft_render`/`weft_mix`/`weft_import`'s own error paths, `SIM_SOURCE_CONFLICT`/`INVALID_TICKS` at the MCP layer, and — most notably — what happens when `rmcp`'s own JSON-schema deserialization rejects a malformed call *before* a tool body runs at all. That path bypasses `CliError` entirely and would surface as a raw protocol-level error, which AGENTS.md itself calls "a bug worth filing" if it ever happens undetected.

## Positives worth naming (so they don't get lost in a list of problems)

- Determinism discipline has held almost everywhere it matters — the two real violations found (animation-clip hashing, the physics write-back loop's latent risk) are narrow and specific, not systemic.
- The CLI/MCP structured-error contract (`{code, message, context}`) is real and consistently applied across almost the entire surface — the gaps found are at the edges (panics in two systems, MCP schema-rejection path), not the common case.
- `docs/roadmap/completed-phases.md` and `AGENTS.md`'s operation table were both fully current through Phase 14 at review time — the staleness found was isolated to README.md/ROADMAP.md's higher-level framing, not the detailed records.
- `games/sandbox`'s existing tests assert real, specific behavior (exact positions, exact HUD strings, a regression test for a previously-shipped bug) rather than "it ran."
- Repo hygiene is clean: `Cargo.lock` tracked, `.gitignore` scoped tightly, no build artifacts accidentally committed.
