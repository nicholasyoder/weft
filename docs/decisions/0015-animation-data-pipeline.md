# ADR-0015: Animation data pipeline

- **Status**: accepted
- **Date**: 2026-09-01

## Context

Tier 1's capability audit named the animation data pipeline the most structurally invasive item left in that tier: the vertex format carried no bone index/weight data, `gltf_import.rs` never read `document.skins()`/`document.animations()` at all, and no runtime skeletal playback existed. The roadmap deliberately sequenced this ahead of Tier 2's PBR/normal-map work because both touch the vertex format — doing this first means one vertex-format migration instead of two. The user picked this item explicitly over audio and Tier 2's physics gameplay substrate.

Scope, confirmed up front: the format change, glTF animation import, and *basic* runtime skeletal playback (one clip, plays/loops, deterministic). Blending, state machines, multiple simultaneous clips, root motion, and IK are explicitly out — Tier 3+.

**The constraint that shaped the whole design**: `engine-assets`' content-addressed store hashes the *encoded bytes* of `MeshData` (`store.put` hashes what it's given), not any source file. `bincode` encoding is positional, not tagged — adding fields to `MeshData` would change the hash of every existing stored mesh, breaking every scene file and test fixture that references one by hash. ADR-0005 named animation as deferred work but didn't anticipate this specific hash-stability problem.

## Decision

**Three new sibling asset types, `MeshData` left untouched.** `crates/engine-assets/src/{skin,skeleton,animation}.rs` — `SkinData` (per-vertex joint indices/weights, vertex-index-aligned to `MeshData.positions`, ≤4 influences/vertex per glTF's `JOINTS_0`/`WEIGHTS_0` convention), `Skeleton` (a joint hierarchy stored **root-first** — `joints[i].parent < i` always — so sampling never needs sorting or recursion), and `AnimationClip` (keyframe tracks). Each is independently content-addressed; an unskinned mesh's hash, and every asset already checked in, is completely unaffected.

`Skeleton` and `AnimationClip` are deliberately two separate types, not one combined type, even though this phase imports only one clip per skeleton. This is the one deliberate exception to "don't generalize speculatively" (contrast Phase 9's despawn-hook precedent, which declined to build a hook mechanism for a hypothetical second consumer): Tier 3's multi-clip/blending work is already named as the *next* consumer of exactly this split, and splitting now costs one extra `store.put()` call versus a second breaking asset-format migration later.

**GPU skinning via a storage buffer, not CPU skinning or a fixed uniform array.** A new `SkinnedVertex`/`SkinnedMeshData`/`from_skinned_asset` in `engine-render::mesh` join a mesh's plain geometry with its separately-stored `SkinData` at draw time, entirely independent of the storage-format decision above. `skinned_shader.wgsl` adds a third bind group, `@group(2) var<storage, read> joint_matrices: array<mat4x4<f32>>`, blending up to 4 weighted joint matrices before the existing model/view/light math — otherwise identical to `shader.wgsl`. A storage buffer (not a fixed-size uniform array) means no compile-time max-joint-count. This is the third instance of "second shader + second pipeline appended to one pass" after ADR-0014 established the pattern for text — `RenderContext` gained a `skinned_pipeline_for` mirroring `pipeline_for` (opaque, same depth settings — not alpha-blended like the UI pass) and a `skin_cache: HashMap<(mesh_hash, skin_hash), MeshBuffers>`, the fourth instance of the lazy-cache-by-hash shape mesh/texture/font caches already established.

**`JointPalette` lives in `engine-core`, not `engine-anim`.** This is a correction made mid-implementation, not the original plan: the first design put the computed joint-matrix-palette component in `engine-anim` alongside `Animator`. Building the actual `engine-render` integration surfaced the real problem — `engine-render` needs to read `JointPalette` off entities by its concrete Rust type (hecs components are matched by `TypeId`, so the reading crate must literally import the producing crate's type), which would force a new `engine-render → engine-anim` dependency edge purely to name one type. `Transform` already solves exactly this shape of problem for `engine-physics`: it's produced by simulation and consumed by rendering, so it lives in `engine-core`, which both `engine-physics` and `engine-render` already depend on. `JointPalette` is the identical relationship for animation, so it moved to `engine-core::joint_palette`, with `engine-anim` re-exporting it (`pub use engine_core::JointPalette;`) so its own public API is unchanged. `Animator` (scene-authored input, not computed output) correctly stays in `engine-anim`, mirroring how `RigidBody`/`Collider` stay in `engine-physics` rather than `engine-core`.

**New `crates/engine-anim` domain crate**, mirroring `engine-physics`'s precedent of a dedicated crate off `engine-core`/`engine-assets` rather than living inside `engine-render`: animation must advance every tick even with no renderer present, since `run`/`test`/`inspect` are headless by default. Contains `Animator` (scene-authorable: `skeleton`/`clip` hashes, `playing`/`looping`/`speed`/`time`), `sampling::sample()` — a **pure function** of `(skeleton, clip, time)` with no tick/RNG/wall-clock access, doing piecewise-linear TRS interpolation between keyframes (rotation via `Quat::lerp`, i.e. nlerp, not true slerp) composed root-first into world matrices then multiplied by each joint's inverse bind matrix — and `animation_step`, registered like `physics_step`, which advances `Animator.time` by `dt * speed` and writes the resulting `JointPalette`. `AnimCache` (a `Resources` entry, same lazy-decode-by-hash shape as the render caches) avoids re-decoding skeleton/clip bytes every tick.

**A new `engine_core::AssetsDir` resource, and `--assets-dir` on `test`/`run`/`inspect`/`replay`** (previously only `render`/`play`/`import` had it) — a genuinely new plumbing requirement, not scope creep. `animation_step` is the first per-tick *simulation* system needing read access to the content store; until now nothing but rendering ever touched it. `SimSource::build` inserts `AssetsDir` into every `Sim`'s `Resources`. Every existing call site (~15+ tests, `watch.rs`, `render_scene`) keeps compiling unchanged via default-`"assets"`-delegating wrappers (`build_sim`, `run_and_dump`, `run_and_dump_snapshots`, `verify_scenario_determinism`) alongside new `*_with_assets_dir` siblings taking an explicit path — the same pattern `step_and_dispatch`/`step_and_dispatch_with_input` established in ADR-0013 for `Input`. `engine-mcp`'s `RunParams`/`TestParams`/`InspectParams`/`ReplayParams` gained a matching `assets_dir` field.

**Failure posture for a bad asset reference inside `animation_step`**: a missing `AssetsDir` (no asset store configured at all) is a silent no-op — a legitimate engine-wide state, the same posture `PhysicsState::apply_force` already has for a missing body handle. An *unresolvable hash*, once an `AssetsDir` does exist, panics with a clear message instead — `System = fn(&mut SystemArgs)` has no `Result`-returning path to produce a structured `{code, message}` error through, so a loud panic is the closest available equivalent to this codebase's usual failure discipline, not a second silent case.

**Rendering a skinned mesh with no `JointPalette` yet falls back to an ordinary static draw** in bind pose (ignoring `MeshRef.skin`), rather than guessing a joint count or hard-failing — covers a `MeshRef.skin` authored with no `Animator`/`"animation"` system wired up. `MeshRef` gained `skin: Option<String>` (`#[serde(default)]`, additive — every existing scene file's `MeshRef` needed no changes beyond three struct-literal test call sites gaining `skin: None`).

**Correctness fix to ADR-0005 decision 4, skinned meshes only**: the importer bakes a mesh node's accumulated world transform into stored vertex positions — but per the glTF spec, a *skinned* mesh's own node transform is ignored for skinning purposes (only joint transforms matter). Baking it in anyway would silently double-transform. `import_gltf` now skips this baking specifically when the mesh's node has a skin attached; unskinned import is completely unaffected. Proven by a hand-built fixture (`crates/engine-assets/tests/fixtures/skinned.gltf`) whose mesh node carries a deliberate non-identity `[5, 0, 0]` translation, asserting the stored positions come back untouched.

**glTF import**: skin/joint data rides the same primitive already being read (no widening of the existing single-mesh/single-primitive restriction). At most one skin and one animation per file — `ASSET_GLTF_UNSUPPORTED` otherwise, the same scope-limiting-by-structured-error pattern as the existing mesh/primitive count checks. A `JointOrdering` helper reorders `skin.joints()` (which carries no ordering guarantee) into `Skeleton`'s required root-first order via a stable BFS from root joints, and remaps both the per-vertex `JOINTS_0` indices and animation channel target nodes through the same mapping. `ImportedAsset` gained `skin_hash`/`skeleton_hash`/`clip_hash: Option<String>`, flowing through `ImportResult`, `gltf_fragment` (emitting an `[entity.components.Animator]` block), and `weft_import`'s MCP response.

**Test asset: hand-built, not Blender-generated.** A minimal two-joint quad (`skinned.gltf`/`.bin`, constructed directly as JSON + a packed binary buffer) gives exact, fully-controlled numeric expectations for both the import-time correctness test and the runtime `JointPalette` assertions — versus a Blender-generated rig, whose exact output would need to be inspected *after* generation rather than predicted, and which adds a real toolchain dependency for no additional coverage this phase actually needs. `tools/asset-gen/generate_crate.py`'s headless-Blender pattern remains the right tool for a *visually real* animated prop, deferred until `games/sandbox` has a concrete need for one (no such need existed yet at this phase's end).

## Alternatives considered

- **Folding skin/skeleton/animation fields directly into `MeshData`**, as ADR-0005's "revisit when" section originally anticipated. Rejected once the hash-stability problem above was understood: every existing stored mesh's content hash would change, breaking every scene file and fixture that references one.
- **CPU skinning** (recompute vertex positions on the CPU, re-upload every frame). Rejected: breaks `mesh_cache`'s "static buffer uploaded once" model for every animated entity, every frame — GPU skinning keeps the base mesh buffer fully static and only re-uploads a small per-draw joint palette.
- **A fixed-size uniform array for joint matrices** instead of a storage buffer. Rejected: forces a compile-time max-joint-count decision with no concrete need yet to inform one; a storage buffer scales to whatever the skeleton actually has.
- **`JointPalette` as a `Resources`-keyed `HashMap<Entity, _>`** instead of a component. Rejected: would duplicate ADR-0011's despawn-eviction logic for no benefit — a component already rides hecs's own per-entity storage and is cleaned up automatically when an entity despawns.
- **Combining `Skeleton` and `AnimationClip` into one asset type.** Rejected — see "three new sibling asset types" above; would force a second breaking migration once Tier 3's multi-clip work lands.

## Consequences

- `engine-assets`, `engine-core`, `engine-render`, and `engine-cli`/`engine-mcp` all changed; a new `engine-anim` crate joined the workspace. The `Resources`/`ComponentRegistry`/`SystemRegistry` extension points (ADR-0003/0008) and the lazy-cache-by-hash pattern (established for meshes, generalized to textures/fonts in ADR-0014) both generalized to a fourth and fifth consumer respectively with zero new mechanism — only `AssetsDir` and the skinned vertex/pipeline/shader trio were genuinely new.
- `--assets-dir` now exists on every batch CLI command, not just rendering ones — a real (if narrow) CLI/MCP surface expansion beyond what "add a new component/system" phases have typically needed.
- Rotation interpolation is nlerp, not true slerp — acceptable for this phase's scope; revisit if a large per-keyframe rotation delta ever produces a visible non-constant-angular-velocity artifact.

## Revisit when

- Tier 3's animation blending/crossfade or state-machine work begins — this is the anticipated second consumer of the `Skeleton`/`AnimationClip` split.
- A scene needs more than one simultaneous clip driving one skeleton.
- Root motion extraction, IK, or `JOINTS_1`/`WEIGHTS_1` (>4 influences/vertex) become a concrete need.
- Visible artifacts from nlerp-vs-slerp rotation interpolation appear in a real animated asset.
- A per-tick simulation system needs to surface a *structured* error (not a panic) for bad scene-authored data — the `System = fn(&mut SystemArgs)` signature has no channel for this today; `animation_step`'s unresolvable-hash panic is the first time this gap mattered.
- `games/sandbox` has a concrete need for a real animated prop — generate one via `tools/asset-gen`'s headless-Blender pattern then, following `generate_crate.py`'s precedent, rather than building the tooling speculatively now.
