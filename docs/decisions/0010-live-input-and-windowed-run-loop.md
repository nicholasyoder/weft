# ADR-0010: Live windowed input via a fixed-timestep accumulator, and `games/sandbox` as an external registry consumer

- **Status**: accepted
- **Date**: 2026-09-01

## Context

Phase 8 ([ROADMAP.md](../../ROADMAP.md)) needed a first real playable milestone in a new `games/sandbox` crate — a physics playground where the player rolls a ball around an arena using the existing `rapier3d` integration (`crates/engine-physics`). Building it surfaced that the engine had no live/windowed run mode, no wall-clock pacing, and no input capture at all: every command through Phase 6 (`run`, `test`, `inspect`, `replay`, `render`) batch-executes a fixed tick budget as fast as possible and exits. Phase 2's roadmap text ("a windowed mode via winit is a thin wrapper... presents the same offscreen frames to a swapchain") was aspirational and never built — confirmed by grepping the whole workspace for `winit`, which had zero hits before this phase.

This ADR also covers a second, related decision forced by the same milestone: `games/sandbox` needed to define its own game-specific component (`PlayerControl`) and system, not have it baked into `engine-cli`'s own registry — the literal point of Phase 8 per `ROADMAP.md` ("a real crate/project using the engine, not a hardcoded engine-cli scenario").

## Decision

**Input**: a small, deliberately narrow `engine_core::{Input, KeyCode}` (WASD + Space + Escape only, extended on demand) lives in `engine-core` — not a new crate — mirroring how `Transform` was added there in Phase 2 exactly when rendering first needed it. `Input` is not an ECS component; it's inserted into the existing `Resources` bag (ADR-0008) once per frame by the live loop, read by systems via `args.resources.get::<Input>()`. This needed **zero changes** to `Resources`/`Scheduler`/`SystemArgs` — the extension point built for `engine-physics`'s `PhysicsState` generalized to a second, unrelated occupant on the first try.

**Rendering**: `crates/engine-render/src/gpu.rs`'s old one-shot `render()` (rebuilt the entire `wgpu` instance/device/pipeline/mesh-uploads from scratch every call) is split into `GraphicsCore` (instance/adapter/device/queue) and `RenderContext` (shader, layouts, a pipeline cache keyed by color-target format, mesh/texture caches) — built once, reused across many frames. `render_scene`/`render_scene_to_png` keep their exact pre-existing signatures and behavior (verified against the unchanged golden-image test). A new `WindowRenderer` (`src/window.rs`) adds `wgpu::Surface`-based presentation with no CPU pixel readback — the actual perf-relevant difference from the offscreen path, not just context reuse. Backend selection (`wgpu::Backends`) is a plain runtime parameter on every constructor, not a `cfg` split, per the engine's ground rule that a window is a consumer of the headless path, never a separate code path; the offscreen path keeps hardcoding `Backends::VULKAN` (ADR-0004's Mesa-lavapipe posture, unchanged), while `play`'s windowed path defaults to `Backends::PRIMARY`.

**The live loop**: `engine_cli::live::play` (new `crates/engine-cli/src/live.rs`) takes caller-supplied `&ComponentRegistry`/`&SystemRegistry` — like `engine_scene::load` already does — rather than hardcoding `registry::components()`/`registry::systems()` the way `SimSource::build` does, specifically so `games/sandbox` can inject its own extra registrations. It drives a winit 0.30 `ApplicationHandler` with `ControlFlow::Poll` and a standard fixed-timestep accumulator: real elapsed time accumulates (clamped to 0.25s to avoid a catch-up spiral after a stall), `Sim::step()` runs in fixed `sim.dt` increments (preserving ADR-0002's determinism guarantee for each individual tick), and the frame renders once per iteration. A `--max-ticks` auto-exit is the non-interactive escape hatch that makes `engine play` testable in CI/a sandbox with no human at the keyboard — without it, a live loop has no exit condition a test could drive.

**`games/sandbox`**: a new workspace member with both a `[lib]` (`pub mod player_control;`) and a `[[bin]]` target, matching `engine-cli`'s own established shape. Its `main.rs` builds an extended registry — `engine_cli::registry::components()` plus `.register("PlayerControl", ...)` — and calls `engine_cli::live::play` with it. This is the concrete proof that `ComponentRegistry`/`SystemRegistry::register` (already `pub`, already chainable on an externally-held instance) and `engine_cli::registry::components()`/`systems()` (already plain `pub fn`) support exactly this extension pattern with **zero new mechanism** — the same "ADR-0003 registry design needed nothing new" result every phase since Phase 1 has confirmed, now for a fourth-or-fifth time and the first time from *outside* `engine-cli` entirely.

`PlayerControl` (a per-entity force-tuning component) and `player_control_system` (reads `Input`, computes a WASD direction, applies a force to every tagged entity) live in `games/sandbox`, not `engine-physics` — a game concept, not an engine one. It needed one small, justified addition to `engine-physics` first: `PhysicsState::apply_force(entity, force, wake_up) -> bool`, since `PhysicsState.bodies` was previously private with no accessor at all. It's engine-native (no `rapier3d::RigidBodyHandle` leaks out) and a silent no-op (not a panic) if the entity isn't registered yet — the first tick after spawn, before `physics_step` has lazily registered it.

## A real bug found and fixed during this phase

Adding concurrent multi-threaded test execution against the refactored `gpu.rs` surfaced an intermittent SIGSEGV (~30-50% of `cargo test -p engine-render` runs) that did **not** reproduce on the pre-refactor code (confirmed via `git stash`, 10/10 clean baseline runs vs. repeated failures on the refactor). Root-caused with `gdb` (installed for this purpose) to a crash inside `libvulkan.so.1`, called from `wgpu_hal::vulkan::DeviceShared::set_object_name` (the `VK_EXT_debug_utils` "set object name" call wgpu-hal makes automatically for every labeled resource when `InstanceFlags::DEBUG`/`VALIDATION` are set — which is wgpu's default in debug builds, via `InstanceFlags::from_build_config()`). This is a concurrency bug in the Vulkan loader's debug-utils object-naming path under multiple threads creating labeled Vulkan resources at once, not a logic bug in Weft's own code — but the refactor's timing changes evidently made the race far more likely to hit in this sandbox's Mesa/lavapipe setup. Fixed by passing `InstanceFlags::empty()` explicitly in `GraphicsCore::make_instance` — debug object-labeling isn't needed at runtime regardless, so removing it both fixes the crash and is the right production posture. Verified with 20/20 clean `cargo test -p engine-render` runs and 3/3 clean full-workspace runs after the fix. Two other changes made while investigating (keeping `GraphicsCore`'s `wgpu::Instance` alive instead of dropping it early; declaring `RenderContext`'s `core: GraphicsCore` field last so struct-field drop order matches the safe dependency order) are kept as defensive precautions but were **not** the actual fix — noted in code comments to avoid a future reader treating an unconfirmed theory as an established fact.

## Alternatives considered

- **`blender-mcp`-style external control, or any AI-model-based input** — not applicable; this is about a human player's keyboard, unrelated to ADR-0009's asset-generation scope.
- **Unify headless and windowed instance construction with a single `InstanceDescriptor` shape carrying a display handle always** — considered and rejected after reading `wgpu` 30's actual source: `InstanceDescriptor::display` is documented as a *platform/compositor connection* (e.g. winit's `OwnedDisplayHandle`), used only by GLES/Wayland — irrelevant to Vulkan/Metal/DX12, which is all this engine ever targets. `Instance::create_surface(window)` derives both window and display handles from the window value itself (`SurfaceTarget::DisplayAndWindow`), so `new_without_display_handle()` works uniformly for both paths; only `compatible_surface` on the adapter request differs.
- **A generic `engine-input` crate** — rejected as premature: `Input`/`KeyCode` is ~30 lines with no winit dependency of its own; a dedicated crate isn't justified until a second, meaningfully different input source exists.
- **Serialize GPU-touching tests with a `Mutex` instead of disabling debug labels** — considered as a defense-in-depth measure once the real cause was found, but not adopted: the root cause is fixed at its source, and forcing test serialization would mask any *future* unrelated concurrency bug instead of surfacing it. May still be worth adding later if another GPU-driver concurrency issue turns up.

## Consequences

- The engine now has a genuinely live, real-time capable rendering path (persistent GPU context, no per-frame instance/pipeline rebuild) — a prerequisite this phase needed anyway, not scope creep: the old one-shot `render()` could not have sustained interactive framerates.
- `games/sandbox` is the first crate outside `crates/engine-*` in the workspace, and the first proof that the engine's own CLI crate (`engine-cli`) is reusable as a library dependency by a downstream game, not just a binary.
- No `AGENTS.md`/MCP surface gained a `play` tool — deliberately, same posture as `--watch`'s existing CLI-only status.
- `InstanceFlags::empty()` means Vulkan validation layers are now off by default for all of Weft's rendering, headless and windowed alike (previously implicitly on in debug builds). If a future rendering bug needs validation-layer diagnostics, that's an opt-in local debugging step, not a default the whole test suite should pay a driver-stability cost for.

## Revisit when

- Recording/replaying a `play` session becomes a real, concrete need — right now `Recording.inputs` stays the Phase-0-era placeholder it's always been.
- A second real game (or a second engine consumer of `Input`) shows `KeyCode`'s current WASD+Space+Escape scope is too narrow, or shows `Input`/`engine-core` isn't the right home after all.
- `--watch`'s "tear down and rerun from scratch" model needs to compose with `play`'s live window — not attempted this phase; `watch.rs`'s rebuild-everything approach doesn't obviously fit a process holding live GPU resources and keyboard focus.
- Any other GPU-driver-level concurrency flake turns up in this sandbox's Mesa/lavapipe setup — at that point, add the `Mutex`-based test serialization considered and deferred above, rather than re-diagnosing from scratch.
